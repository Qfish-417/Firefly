## STAR 展开（面试口述用，不进简历正文）

简历正文用的是"小标题 + 量化结果"的紧凑写法；下面这份 STAR 是同一批事实的口述版本，
面试被要求"讲一个你做过的项目"时按这个顺序说。

### 版本 A：检索优化（推荐，最能体现方法论）

**S｜情境**
三 Agent 教育平台的教学决策必须由检索证据支撑。但当时检索质量从未被量化——"能用"只是主观印象，
而合成语料上所有指标都很漂亮。

**T｜任务**
建立可复现的评测口径，把真实文档语料上的 Recall@10 提升到 0.85 以上，并确认这些数字反映真实能力。

**A｜行动**
1. **先修口径**。原本用"同一文件的全部 chunk"当 gold set，`big-integer/README.md` 的 58 个 chunk
   全被算成与 "how do I use big integer" 相关，包括 `#### shiftLeft(n)`——它与查询没有任何词汇或
   语义重叠，任何检索器都不该把它排进前 10，分母虚高一个量级。改按 h1–h4 小节划分后，实测 4058
   个小节里 99% 含 1~5 个 chunk，与 MS MARCO 量级一致。
2. **定位再动手**。统计正确答案在 200 深度内的排名分布：第 1 位 44%、2~10 位 37%、11~200 位
   13.6%、未召回 5.7%。前 10 合计 80.7%，理论可达 94.3%——说明大部分答案检索得到，问题在排序与
   管线损耗，不在召回能力。
3. **逐项实测，排除 6 条无效杠杆**。候选窗口 24→200 只 +1.3% 后饱和；重排 -1.6%~-0.3%；兄弟 chunk
   扩展 -2.7%；RRF 常数 10/20/40/60 与双腿权重 1:1~5:1 全部落在 0.764~0.776。全部卡在 0.75~0.78，
   据此判定瓶颈不在融合层。
4. **转向索引侧**。发现两个缺陷：小节被切成多块时只有第 1 块带标题行（前 800 个 chunk 仅 77% 以
   标题开头）；文档标识只存在 `entity_keys` 里、不在可检索文本中。补齐上下文，并加上 Qwen3 查询侧
   instruct 前缀。

**R｜结果**
Recall@10 **0.706 → 0.912**（5303 chunk / 300 查询）；词法腿 0.543 → 0.868；多 chunk 小节
0.502 → 0.692；检索 p50 299ms。全过程写入评测报告，含 6 条被自己的测量推翻的结论。

### 版本 B：架构设计

**S｜情境**
三个 Agent（学习总监、学习科学家、体验工程师）需要协作，而教学改动作用在真实学习者身上——
不可逆的自动化在这里是缺陷，不是效率。

**T｜任务**

**A｜行动**

**R｜结果**
12 个包、40 张表、18 个迁移、47 份 ADR，3.4 万行 TypeScript；三 Agent 闭环可从
`awaiting_approval` 走到 `state=learned`，9 次状态迁移全部可查；0 契约违规；270 项测试全绿。

## 追问准备

> 面试前建议直接看 **[`docs/interview.md`](./interview.md)** —— 那份把 60 秒开场、STAR 口述、
> 8 个必问问题与核心数字速查整合在一处，不含本文档的文案取舍内容。下面是同一批答案的原始版本。

### Q：R@10 = 0.912 是怎么算的？

`前 10 条命中数 / gold set 大小`。除以 10 得到的是 Precision@10 —— 这两个必须分开，
如果 Recall 也除以 10，它会与 Precision 位位相同（这个 bug 项目里真出现过：11 场景 × 3 cutoff
全部 `Recall@k == Precision@k`）。

gold set 按 h1–h4 小节划分，实测 4058 个小节里 99% 含 1–5 个 chunk。此前用"同一文件的全部 chunk"
是错的：`big-integer/README.md` 的 58 个 chunk 全被算成与 "how do I use big integer" 相关，
包括 `#### shiftLeft(n)`，它与查询无任何词汇或语义重叠。分母虚高一个量级，R@10 被压到 0.274。

### Q：0.912 里有没有作弊 / 标签泄漏？

有条件，我在报告里明写了。文档标识的收益依赖查询提供来源（"在 X 文档里找 Y"），查询去掉来源后
收益消失（0.783 vs 无标识的 0.799）。

判定它不是泄漏的三条证据：标识只到*文件*层而 gold set 是 (文件, 小节)，exceljs 的 100+ 小节共享
同一标识；标题唯一组 0.914 与标题重复组 0.905 几乎相同（若只是消歧，重复组才该独涨）；R@1 仍只有
0.565，说明仍需在同文件上百小节中排序。

中途另有一个 0.863 的做法（从查询解析来源、给同源 chunk 加权）被我放弃了——那是给 RRF 外挂特判，
且依赖我自己构造的查询格式。

### Q：为什么引用精确率只有 0.218？

这是两个目标的固有冲突，不是缺陷。gold set 均值 1.34 而证据包给 8.28 条，算术上限约
1.34/8.28 = 0.162，实测 0.218 就在上限附近。最大化 R@10 要求返回 10 条，最大化引用精确率要求
只给 1–2 条。两个数一起报，让权衡可见。

### Q：重排为什么关掉？换个重排器会不会是正收益？

在**本项目条件下**实测有害：0.910 → 0.875，还多花约 120ms，所以默认关闭。

但我不会把它说成「重排没用」，因为这个结论有明确的适用边界，两个条件都成立才成立：

1. **用的不是专用重排器**。这里是 embedding 模型兼挂的 `/v1/rerank`，不是专门训练的
   cross-encoder（如 `bge-reranker-v2-m3` 那类）。换成专用重排器需要重测。
2. **基线已接近饱和**。修完索引侧缺陷后基线已是 0.910，重排能补的边际信息很少。若基线在 0.4~0.6
   区间，重排通常有明显收益。

跑这个实验时还顺带发现本地 `/v1/rerank` 忽略请求里的 `top_k`（请求 3 条、给 5 篇文档，返回 5 条），
而客户端断言"恰好 top_k 条"，导致整条重排链路对这类 provider 完全不可用——尽管它的打分本身正确。
已改成"至少 top_k 条 + 客户端按分数降序自己截断"。

### Q：哪些结论被你自己的测量推翻了？

报告第 0.5 节专门记录，这是我认为最该读的部分：

| 曾经的结论 | 推翻它的证据 |
|---|---|
| 质量随语料规模上升 | 相关集随语料一起变大造成的假象；固定相关集后 16 倍规模差异下 nDCG 0.680→0.687 |
| halfvec 有 31% 精度损失 | 两个探针 bug（`SET LOCAL` 事务外静默无效、ANN 索引未按 `index_version_id` 分区）；修正后 fp16 舍入召回 1.000，损失全来自 HNSW 近似 |
| 自适应 k 能提升召回 | 相关/不相关候选的 `score/best` 分布几乎重合（p50 0.520 vs 0.492），RRF 归一化比不携带相关性信号 |
| 召回差是查询用词与文档不一致 | 换成文档标题当查询，召回从 52% **降到** 31% |
| HyDE 能提升检索 | 全局重写使词法 P@10 降 14%、p50 增 958ms；只作零结果兜底才是净收益 |
| 满意度可由 LLM 裁判代表 | 独立标注与裁判 `completeness` 的 Pearson r 仅 0.248 |

### Q：已知的不足？

- 跨主体聚合缺失：`t.ambig.cross-subject` 3/3 失败。检索合同只支持单主体计数与两主体比较，
  正确行为是报告能力缺失，模型却回退到 `retrieval/exploratory`。这是边界不是回归（clear 档 1.000）。
- ANN 索引未按 `(tenant_id, index_version_id)` 分区；`hnsw.iterative_scan` 未接进产品代码。
- 检索身份 HMAC 无 nonce 且未绑定请求体，±30s 内可重放。
- 满意度只有 LLM 打分，缺真人标注。
