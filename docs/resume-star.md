## 简历条目（可直接粘贴）

### 版本 A：偏 RAG / 检索工程

**FireFly QuestLab · RAG 检索系统**（个人项目，TypeScript / PostgreSQL + pgvector / 本地部署 Qwen3）

- **S** 三 Agent 教育平台需要一套可信的 RAG：Agent 的教学决策必须由检索证据支撑，而当时检索质量
  从未被量化，"能用"只是主观印象。
- **T** 建立可复现的检索评测口径，并把真实文档语料上的 Recall@10 提升到 0.85 以上。
- **A** 先修正评测口径本身（gold set 从"整个文件"改为 h1–h4 小节，对齐 MS MARCO 的 1–5 篇量级），
  再按"排名分布 → 定位瓶颈 → 逐项实测"推进：实测排除 6 条无效杠杆（`candidate_k` 24→200 仅
  +1.3%、重排 **-1.6%**、兄弟 chunk 扩展 -2.7%、RRF 常数与权重全在 0.764–0.776），据此判定瓶颈
  不在融合层，转向索引侧，修复 chunk 丢失标题上下文与文档标识不可检索两个缺陷，并补上 Qwen3
  查询侧 instruct 前缀。
- **R** **R@10 0.706 → 0.912**（5303 chunk / 300 查询，gold set 1–8）；词法腿 0.543 → 0.868；
  多 chunk 小节 0.502 → 0.692；检索 p50 299ms。全过程写入评测报告，含 6 条被自己的测量推翻的结论。

### 版本 B：偏 Agent / 系统工程

**FireFly QuestLab · 三 Agent 运行时与模型网关**（个人项目，TypeScript / Node 24 / PostgreSQL）

- **S** 三个 Agent（学习总监、学习科学家、体验工程师）需要在同一事务边界内协作，且教学改动必须
  可审计、可回滚。
- **T** 设计契约优先的运行时：Agent 输出全部经 JSON Schema 校验，token 与成本有唯一事实来源，
  并建立五维能力评测。
- **A** 落地 Outbox/Inbox + 版本化 Task + append-only Event 的持久化骨架（40 张表）；模型网关按
  `provider × route` 路由，token/成本只认 `model_invocation` 审计账本与原子 `run_budget_usage`；
  能力评测刻意让五个维度事实来源互不共享（工作流事实表 / 状态迁移 / 生产校验函数 / 账本 /
  独立 LLM 裁判），避免一个指标掩盖另一个。
- **R** 端到端综合 **0.979**：任务完成 6/6、步效率 9/9 最小迁移、工具正确率 0.952、
  1507 token/run（基线 3000）、12 次模型调用 0 失败 0 重试、0 契约违规；245 单元 + 36 集成测试全绿。

### 版本 C：偏"发现并修复缺陷"（最能体现工程判断）

**FireFly QuestLab · 评测驱动的缺陷定位**

- **S** 合成语料上各项指标都很漂亮，但没人验证过这些数字是否成立。
- **T** 换真实文档重跑，确认指标是否反映真实能力。
- **A** 构建真实语料（仓库内 5303 个人写 Markdown chunk，中英混排）并逐项归因。
- **R** 测出 **5 个合成语料完全掩盖的缺陷**：英文自然句词法检索 96/96 零结果（hybrid 静默退化为
  向量单腿）、证据层把同文件段落当重复丢弃（每来源只留 1 条）、Markdown 表格查询直接抛异常、
  chunk 丢失标题上下文、重排 provider 忽略 `top_k` 导致整条重排链路不可用。同时发现并修正评测
  自身 5 处缺陷（含"评测报告进了语料且逐字包含查询文本"）。

## 追问准备

### Q：R@10 = 0.912 是怎么算的？

`前 10 条命中数 / gold set 大小`。除以 10 得到的是 Precision@10 —— 这两个必须分开，
如果 Recall 也除以 10，它会与 Precision 位位相同（这个 bug 项目里真出现过：11 场景 × 3 cutoff
全部 `Recall@k == Precision@k`）。

gold set 按 h1–h4 小节划分，实测 4058 个小节里 99% 含 1–5 个 chunk。此前用"同一文件的全部 chunk"
是错的：`big-integer/README.md` 的 58 个 chunk 全被算成与 "how do I use big integer" 相关，
包括 `#### shiftLeft(n)`，它与查询无任何词汇或语义重叠。分母虚高一个量级，R@10 被压到 0.274。

### Q：0.912 里有没有作弊 / 标签泄漏？

有条件，我在报告里明写了。文档标识的收益依赖查询提供来源（"在 X 文档里找 Y"），查询去掉来源后
收益消失（0.783 vs 无标识的 0.799）。

判定它不是泄漏的三条证据：标识只到*文件*层而 gold set 是 (文件, 小节)，exceljs 的 100+ 小节共享
同一标识；标题唯一组 0.914 与标题重复组 0.905 几乎相同（若只是消歧，重复组才该独涨）；R@1 仍只有
0.565，说明仍需在同文件上百小节中排序。

中途另有一个 0.863 的做法（从查询解析来源、给同源 chunk 加权）被我放弃了——那是给 RRF 外挂特判，
且依赖我自己构造的查询格式。

### Q：为什么引用精确率只有 0.218？

这是两个目标的固有冲突，不是缺陷。gold set 均值 1.34 而证据包给 8.28 条，算术上限约
1.34/8.28 = 0.162，实测 0.218 就在上限附近。最大化 R@10 要求返回 10 条，最大化引用精确率要求
只给 1–2 条。两个数一起报，让权衡可见。

### Q：重排为什么关掉？

实测有害：0.910 → 0.875，还多花约 120ms。跑这个实验时顺带发现本地 `/v1/rerank` 忽略请求里的
`top_k`（请求 3 条、5 篇文档，返回 5 条），而客户端断言"恰好 top_k 条"，导致整条重排链路对这类
provider 完全不可用——尽管它的打分本身正确。已改成"至少 top_k 条 + 客户端按分数截断"。

### Q：哪些结论被你自己的测量推翻了？

报告第 0.5 节专门记录，这是我认为最该读的部分：

| 曾经的结论 | 推翻它的证据 |
|---|---|
| 质量随语料规模上升 | 相关集随语料一起变大造成的假象；固定相关集后 16 倍规模差异下 nDCG 0.680→0.687 |
| halfvec 有 31% 精度损失 | 两个探针 bug（`SET LOCAL` 事务外静默无效、ANN 索引未按 `index_version_id` 分区）；修正后 fp16 舍入召回 1.000，损失全来自 HNSW 近似 |
| 自适应 k 能提升召回 | 相关/不相关候选的 `score/best` 分布几乎重合（p50 0.520 vs 0.492），RRF 归一化比不携带相关性信号 |
| 召回差是查询用词与文档不一致 | 换成文档标题当查询，召回从 52% **降到** 31% |
| HyDE 能提升检索 | 全局重写使词法 P@10 降 14%、p50 增 958ms；只作零结果兜底才是净收益 |
| 满意度可由 LLM 裁判代表 | 独立标注与裁判 `completeness` 的 Pearson r 仅 0.248 |

### Q：已知的不足？

- 跨主体聚合缺失：`t.ambig.cross-subject` 3/3 失败。检索合同只支持单主体计数与两主体比较，
  正确行为是报告能力缺失，模型却回退到 `retrieval/exploratory`。这是边界不是回归（clear 档 1.000）。
- ANN 索引未按 `(tenant_id, index_version_id)` 分区；`hnsw.iterative_scan` 未接进产品代码。
- 检索身份 HMAC 无 nonce 且未绑定请求体，±30s 内可重放。
- 满意度只有 LLM 打分，缺真人标注。
