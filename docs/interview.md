# FireFly QuestLab — 面试应答手册

面试前只需要看这一份。所有数字都是实测的，可用 `docs/evaluation-report.md` 末尾的命令复现。

**用法**：先背第 1 节的 60 秒介绍，再看第 2 节挑一个 STAR 版本，第 3 节是必被问到的 8 个问题。
第 4 节是被问住时的标准答法。

---

## 1. 60 秒开场（背下来）

> 这是一个自进化的教育 Agent 平台。给每个学习者生成长期项目任务世界，再根据真实学习效果持续
> 改进教学策略。三个 Agent 分工：学习总监做教学决策，学习科学家做效果分析，体验工程师改代码。
>
> 我负责整体架构和 RAG 检索。架构上的核心决定是让三个 Agent 之间**不通过自由文本接力**——
> Control Plane 用版本化 Task 派活，Agent 用 append-only Event 回报事实，PostgreSQL 工作流
> 状态是唯一事实源。这样每个教学决策都可回放、可回滚、需人工批准。
>
> 检索这块我做的主要是量化。真实文档语料上 Recall@10 从 0.706 优化到 0.912，过程中发现并修复了
> 5 个只有真实文档才会暴露的缺陷。整个项目 3.4 万行 TypeScript，270 项测试。

**如果只让说一句**：三 Agent 教育平台的架构与 RAG，真实语料上 Recall@10 做到 0.912，
端到端五维评测综合 0.979。

## 2. STAR 口述（挑一个，别全背）

### 版本 A：检索优化（默认用这个）

**S 情境**：三 Agent 平台的教学决策必须由检索证据支撑，但检索质量从未被量化——"能用"只是主观
印象，而合成语料上所有指标都很漂亮。

**T 任务**：建立可复现的评测口径，把真实文档语料的 Recall@10 提到 0.85 以上，并确认这些数字
反映真实能力。

**A 行动**（四步，按顺序说）：

1. **先修口径**。原本用"同一文件的全部 chunk"当 gold set，`big-integer/README.md` 的 58 个
   chunk 全被算成与 "how do I use big integer" 相关，包括 `#### shiftLeft(n)`——它与查询没有
   任何词汇或语义重叠。分母虚高一个量级。改按 h1–h4 小节划分后，99% 的小节含 1~5 个 chunk。
2. **定位再动手**。统计正确答案在 200 深度内的排名分布：第 1 位 44%、2~10 位 37%、未召回 5.7%。
   前 10 合计 80.7%，理论可达 94.3%——说明大部分答案检索得到，问题在排序与管线损耗。
3. **逐项实测，排除 6 条无效杠杆**。候选窗口 24→200 只 +1.3% 后饱和；重排 -3.8%；兄弟 chunk
   扩展 -2.7%；RRF 常数与双腿权重全部落在 0.764~0.776。全部卡在 0.75~0.78，判定瓶颈不在融合层。
4. **转向索引侧**。发现 chunk 切分丢失所属标题（前 800 个 chunk 只有 77% 以标题开头），
   文档标识只存在 `entity_keys` 里、不在可检索文本中。补齐上下文并加 Qwen3 查询侧 instruct 前缀。

**R 结果**：Recall@10 **0.706 → 0.912**，词法腿 0.543 → 0.868，检索 p50 299ms。
全过程写进评测报告，含 6 条被自己的测量推翻的结论。

### 版本 B：架构设计

**S**：三个 Agent 需要协作，而教学改动作用在真实学习者身上——不可逆的自动化在这里是缺陷。

**T**：设计一套让每个教学决策都可审计、可回放、可回滚的协作机制。

**A**：Agent 之间不通过自由文本接力、不互改状态。Control Plane 用版本化 `Task` 派活，Agent 用
append-only `Event` 报告事实，大对象走 `ArtifactRef`，PostgreSQL 工作流状态为唯一事实源。
所有 Agent 输出经 JSON Schema 校验；token 与成本只认 `model_invocation` 审计账本与原子
`run_budget_usage`，脚本不自己累加。

**R**：12 个包、40 张表、18 个迁移、47 份 ADR，3.4 万行 TypeScript。三 Agent 闭环可从
`awaiting_approval` 走到 `state=learned`，9 次状态迁移全部可查，0 契约违规，270 项测试全绿。

### 版本 C：缺陷定位（面试官偏好 debug 能力时）

**S**：合成语料上各项指标都很漂亮，但没人验证过这些数字是否成立。

**T**：换真实文档重跑，确认指标反映真实能力。

**A**：构建 5303 chunk 中英混排真实语料，逐项归因每一处落差。

**R**：测出 5 个合成语料完全掩盖的缺陷。最有代表性的是**静默失效**：英文自然句在 PostgreSQL
`simple` 配置下全词 AND 且不去停用词，96/96 查询零结果——系统不报错、正常返回，混合检索已经
退化成向量单腿却无从察觉，只有量化评测才暴露词法腿 MRR 恒为 0。同时发现评测自身 5 处缺陷，
其中包括"评测报告自己进了语料且逐字包含查询文本"。

## 3. 必被问到的 8 个问题

### Q1：Recall@10 = 0.912 怎么算的？

`前 10 条命中数 / gold set 大小`。除以 10 得到的是 Precision@10，两者必须分开——如果 Recall
也除以 10，它会与 Precision 位位相同。这个 bug 项目里真出现过：11 场景 × 3 个 cutoff 全部
`Recall@k == Precision@k`。

gold set 按 h1–h4 小节划分，4058 个小节里 99% 含 1~5 个 chunk，与 MS MARCO 量级一致。

### Q2：0.912 有没有标签泄漏？

**有适用条件，我主动说明**：文档标识的收益依赖查询提供来源（"在 X 文档里找 Y"），查询去掉来源
后收益消失（0.783 vs 无标识 0.799）。

判定不是泄漏的三条证据：

1. 标识只到**文件**层，而 gold set 是 (文件, 小节)——exceljs 有 100+ 小节共享同一标识
2. 标题唯一组 0.914 与标题重复组 0.905 几乎相同。若收益只来自消歧，重复组才该独涨
3. R@1 仍只有 0.565，说明仍需在同文件上百个小节中排序

另外中途有个 0.863 的做法（从查询解析来源、给同源 chunk 加权）**被我放弃了**——那是给 RRF
外挂特判，且依赖我自己构造的查询格式。

### Q3：为什么引用精确率只有 0.218？

**这是两个目标的固有冲突，不是缺陷。** gold set 均值 1.34 而证据包给 8.28 条，算术上限约
1.34/8.28 = 0.162，实测 0.218 就在上限附近。最大化 Recall@10 要求返回 10 条，最大化引用精确率
要求只给 1~2 条。我把两个数一起报，让权衡可见。

### Q4：重排为什么关掉？换个重排器会不会有用？

在**本项目条件下**实测有害：0.910 → 0.875，还多约 120ms。但我不会说成"重排没用"，这个结论有
两个前提：

1. **用的不是专用重排器**——这里是 embedding 模型兼挂的 `/v1/rerank`，不是专门训练的
   cross-encoder（如 `bge-reranker-v2-m3`）。换专用重排器需要重测。
2. **基线已接近饱和**——修完索引侧缺陷后基线已是 0.910，重排能补的边际信息很少。若基线在
   0.4~0.6 区间，重排通常有明显收益。

顺带发现本地 `/v1/rerank` 忽略请求里的 `top_k`（请求 3 条、给 5 篇文档、返回 5 条），而客户端
断言"恰好 top_k 条"，导致整条重排链路对这类 provider 完全不可用——尽管它的打分本身正确。
已改成"至少 top_k 条 + 客户端按分数降序自己截断"。

### Q5：哪些结论被你自己的测量推翻了？（**主动讲，这是加分项**）

| 曾经以为 | 推翻它的证据 |
|---|---|
| 质量随语料规模上升 | 相关集随语料一起变大造成的假象；固定相关集后 16 倍规模差异下 nDCG 0.680 → 0.687 |
| halfvec 有 31% 精度损失 | 两个探针 bug（`SET LOCAL` 事务外静默无效、ANN 索引未按 `index_version_id` 分区）；修正后 fp16 舍入召回 1.000，损失全来自 HNSW 近似 |
| 自适应 k 能提升召回 | 相关/不相关候选的 `score/best` 分布几乎重合（p50 0.520 vs 0.492） |
| 召回差是查询用词与文档不一致 | 换成文档标题当查询，召回从 52% **降到** 31% |
| HyDE 能提升检索 | 全局重写使词法 P@10 降 14%、p50 增 958ms；只作零结果兜底才是净收益 |
| 满意度可由 LLM 裁判代表 | 独立标注与裁判 `completeness` 的 Pearson r 仅 0.248 |

### Q6：三个 Agent 为什么不直接对话？

自由文本接力**无法审计**——出错时说不清是谁的判断错了。改成 Control Plane 用版本化 `Task` 派活、
Agent 用 append-only `Event` 报告事实，每个决策就都能回放。

另外 `Loop Sentinel`（循环哨兵）是确定性平台能力，**不是第四个 Agent**，别答错。

### Q7：「自进化」会不会失控？

不会，因为**每一步都需人工批准**。系统停在 `awaiting_approval` 状态，不批准就不往下走。这是
设计约束而非保守：教学改动作用在真实学习者身上，不可逆的自动化在这里是缺陷。

### Q8：已知的不足？（**坦白讲，别掩饰**）

- **跨主体聚合缺失**：`t.ambig.cross-subject` 3/3 失败。检索合同只支持单主体计数与两主体比较，
  正确行为是报告能力缺失，模型却回退到 `exploratory`。这是**边界不是回归**（clear 档 1.000、
  ambiguous 档 0.889）。
- ANN 索引未按 `(tenant_id, index_version_id)` 分区；`hnsw.iterative_scan` 未接进产品代码。
- 检索身份 HMAC 无 nonce、未绑定请求体，±30s 内可重放。
- 满意度只有 LLM 打分，缺真人标注（实测 LLM 裁判与独立标注 Pearson r 仅 0.248，两个自动打分器
  无法互相印证）。

## 4. 被问住时怎么答

**不知道就说不知道，然后给出你会怎么查。** 这个项目里我自己推翻过 6 条结论，所以"我当时以为
X，实测发现不是"是完全正常的回答方式。

三句可用的话：

- "这个我没测过，我会用……来验证" —— 比编一个答案安全得多
- "我当时的假设是 X，但实测推翻了" —— 见 Q5 那张表
- "这条结论有适用边界" —— 见 Q4 的重排

**绝对不要做的事**：把没测过的数字说成测过的。这个项目所有数字都能追到 `.real-9.json`、
`.e2e-1.json`、`.ans-real.json` 三个结果文件，如果你临场编一个，追问一层就露。
