## 0. 当前结论速览

### 0.1 检索质量：R@10 = 0.912

**R@10 只有一个定义**：`前 10 条里的命中数 / gold set 大小`。除以 10 得到的是 Precision@10，
不是 Recall。此前报告里的"达上限"列是多余的，已删除。

| 语料 | gold set | **R@10** | R@1 |
|---|---|---|---|
| 真实文档（5303 chunk，300 查询） | 1~8（均值 1.34） | **0.912** | 0.565 |

gold set 是**人工标注的、仅针对当前问题最相关的那一小撮文档**，不是"库里所有沾边的内容"。
权威数据集（MS MARCO、KILT）通常只标 1~5 篇。本语料按 h1~h4 小节划分，4058 个小节里 99% 含
1~5 个 chunk，正好落在这个量级。

优化过程见第 23 节，从 0.706 到 0.912 靠两处修复，都是产品缺陷而非调参：

| 阶段 | R@10 | 说明 |
|---|---|---|
| 起点 | 0.706 | |
| 排除评测产物污染 | — | 报告自身进了语料且逐字含查询文本 |
| chunk 补齐标题路径 | 0.769 | 小节被切多块时只有第 1 块带标题 |
| chunk 补齐文档标识 + 查询 instruct 前缀 | **0.912** | 文档标识只存在 entity_keys 里，不可检索 |

**适用条件必须说清楚**：文档标识的收益依赖查询提供来源（"在 X 文档里找 Y"）。实测查询去掉来源
后收益消失（0.783 vs 无标识的 0.799）。这不是标签泄漏——标识只到*文件*层而 gold set 是
(文件, 小节)，exceljs 有 100+ 小节共享同一标识；且标题唯一组 0.914 与标题重复组 0.905 几乎相同，
若收益只来自消歧，重复组才该独涨。

### 0.2 三个指标各自回答什么

| 指标 | 公式 | 回答 |
|---|---|---|
| **P@10** | 命中数 / 10 | 给出的 10 条里几条对（**准不准**） |
| **R@10** | 命中数 / 相关总数 | 该找到的里给出了几成（**全不全**） |
| MRR | 1 / 第一条正确结果的排名 | 第一条对不对 |

`R@k` 的分母必须是相关总数。曾写成 `min(相关总数, k)`，结果 11 场景 × 3 cutoff 全部
`Recall@k == Precision@k` 位位相同，指标白算（第 13 节）。

### 0.4 真实语料测出的三个产品缺陷（均已修）

合成语料完全掩盖了这三个，因为它的 chunk 是 `(topic, facet, depth)` 构造的近重复段落。

| 缺陷 | 表现 | 修复效果 |
|---|---|---|
| 英文自然句词法检索必然零结果 | `simple` 不去停用词且全 AND，96/96 查询零结果，hybrid 静默退化成 vector-only | MRR 0 → 0.724，零结果 96 → 2 |
| 证据层把同文件段落当重复丢弃 | 每来源只留 1 条；检索层已排进前 20 的 11 条正确 chunk 只交出 1 条 | R@10 0.054 → 0.202，P@10 0.232 → 0.480 |
| 查询含 Markdown 表格直接抛错 | 独立 `-` 被解析成 NOT 操作符，表格分隔行压爆 `tsquery stack` | 表格式查询正常返回 |

第三个缺陷值得单独说：它是 PostgreSQL 既有行为（`websearch_to_tsquery('simple', repeat('- ', 60))`
单独就报错），与本仓库改动无关，但会让整次检索**抛异常而非降级**。真实用户不会这么查，可
相似文档推荐、去重、HyDE 生成的假设答案都可能含表格。

### 0.5 被测量推翻的结论

这些是本文档最该读的部分——它们说明哪些测量方式会骗人。

| 曾经的结论 | 推翻它的证据 |
|---|---|
| "质量随语料规模上升"（nDCG 0.462 → 0.582） | 相关集随语料一起变大造成的假象。固定相关集后 16 倍规模差异下 nDCG 0.680 → 0.687，R@10 完全不变 |
| "halfvec 有 31% 精度损失" | 两个探针 bug：`SET LOCAL` 在事务外静默无效；ANN 索引未按 `index_version_id` 分区，`ef_search=40` 的邻居全被过滤掉。修正后 fp16 舍入召回 **1.000**（无损），全部损失来自 HNSW 近似 |
| "自适应 k 能提升召回" | 真实语料上相关/不相关候选的 `score/best` 分布几乎完全重合（p50 0.520 vs 0.492），RRF 归一化分数比不携带相关性信息。启用后 R@10 反降 |
| "召回差是查询用词与文档不一致" | 换成文档自身标题当查询，召回从 52% **降到** 31%。标题只描述文件不描述段落 |
| "HyDE 能提升检索" | 全局重写使词法 P@10 降 14%、MRR 降 14%、p50 增 958ms。只作零结果兜底才是净收益 |
| "R@10 只到上限 43%，检索能力有限" | gold set 定义错了。用"同一文件全部 chunk"当分母，把 `#### shiftLeft(n)` 也算成与 "how do I use big integer" 相关。改按小节划分（99% 落在 1~5 个 chunk，对齐 MS MARCO 量级）后 **R@10 = 0.701、上限 1.000**，同一套检索器涨 2.6 倍 |
| 用户满意度可由 LLM 裁判代表 | 独立标注与裁判 `completeness` 的 Pearson r 仅 **0.248**，32 条里 5 条分歧 ≥2 分且方向不一致。裁判曾为一个缺陷编造理由并打 5 分 |

### 0.55 R@10 只有一个

反复出现的混淆，在此定死：

| 指标 | 公式 |
|---|---|
| **R@10** | 前 10 条命中数 / **gold set 大小** |
| P@10 | 前 10 条命中数 / **10** |

若 Recall 也除以 10，它会与 Precision 位位相同——这个 bug 本项目犯过一次（11 场景 × 3 cutoff 全部
`Recall@k == Precision@k`，见第 13 节）。此前报告里的"达上限"列（`R@10 / min(10,T)*T`）是因为
gold set 曾达 58 才引入的，现在 gold set ≤8、上限恒为 1.000，该列已全部删除。

### 0.6 评测脚本自身的缺陷（已修，记录以免重犯）

| 缺陷 | 后果 |
|---|---|
| `plan_overrides` 字段不存在 | 整轮 `context_k` 扫描静默失效，所有行数字相同 |
| `new PostgresVectorRetriever(db, {...})` 参数形式错 | 向量检索静默缺席，一轮结果实为纯词法 |
| npm scope 被剥离 | `@anthropic-ai/sdk` 变成查询 "how do I use sdk"，96 条里 16 条受影响 |
| 文件级粒度下 5 条查询文本重复 | 同一次检索对一个 topic 正确、对另一个错误，Recall/Precision 双双失效 |
| 评测产物自身进了语料 | `docs/evaluation-report.md` 逐字包含查询文本，48 个 chunk 含 "R@10"，既挤掉正确小节又让检索到报告算"命中" |
| gold set 用"同一文件的全部 chunk" | 分母虚高一个量级，R@10 被压到真实值的 39%（0.274 vs 0.701），并误导出"检索能力只有四成"的结论 |
| 定标用"已选证据"分布反推"候选窗口"阈值 | 循环论证。已选证据本就是选择器留下的高分子集，据此定的 0.84 砍掉 30% 相关候选 |

## 2. 标注与统计口径

标注由语料生成规则决定：每个 chunk 由 `(topic, facet, depth)` 唯一确定，每条查询绑定一个 topic，
因此相关性在构造时就是已知事实，避免用检索结果反推标注。

| grade | 含义 | 数量/查询 |
|---|---|---|
| 3 | 该 topic 的 `definition` facet | 240 |
| 2 | 该 topic 的其他 facet | 720 |
| 1 | 同簇邻近 topic | 视簇大小 |
| 0 | 其余 | — |

命中阈值 `grade >= 2`。nDCG 的 IDCG 由标注统计独立构造，不用结果自身重排。

**p99 口径**：`n < 100` 时第 99 百分位等于最大值，因此所有延迟摘要都输出 `n` 与
`p99_reliable`。RAG 为 32 查询 x 4 重复 = 128 样本（可信）；Agent 并发每档累计 100~120 次
调用（可信）；Agent 单轮墙钟 n=60（不可信，如实标注）。

## 5. 语料规模曲线（hybrid-natural） （结论已被第 17 节推翻：相关集随规模变大造成假象）

| chunk 数 | 向量体积 | MRR | nDCG@10 | R@10 | 证据 | gateway p50（优化前 → 后） | p99（优化前 → 后） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1920 | 15 MB | 1.000 | 0.462 | 0.472 | 4.7 | 179ms → **100ms** | 266ms → 512ms |
| 7680 | 60 MB | 1.000 | 0.529 | 0.506 | 5.1 | 513ms → **164ms** | 1791ms → **532ms** |
| 15360 | 120 MB | 1.000 | 0.541 | 0.534 | 5.3 | 721ms → **263ms** | 973ms → 900ms |
| 30720 | 240 MB | 1.000 | 0.582 | 0.578 | 5.8 | 1111ms → **348ms** | 4829ms → **511ms** |

**质量随语料增大而提升**（nDCG@10 0.462 → 0.582，Recall@10 0.472 → 0.578）。这与修复前的
观察相反：修复前证据被截断在 3.3 条，语料越大干扰越多、指标越差；判据修正后能取满
`context_k`，更大的语料意味着同 topic 的可用证据更多，指标随之上升。四档的质量指标在
第 12 节的优化前后完全一致，逐位复现。

**此前"无法解释的延迟增长"现在有了成因**。旧报告记录：表中 gateway p50 随规模从 179ms 增至
1111ms，而隔离复现同一条链路只有 81~167ms，且纯向量 SQL 在四档上稳定在 2.2~2.7ms。当时排除了
ANN 索引、embedding 单次往返、rerank 交替三个因素，未找到成因。

成因是**授权复查按候选逐条往返**：`RetrievalGateway` 对融合后的每个候选单独执行一次 ACL 查询。
单次只要 1.6ms，隔离测量看不出问题，但候选数随 `fusion_k` 与语料规模一起增长，24 个候选就是
54.7ms，且每一次都是一个独立的数据库往返，尾延迟被逐次累加放大——这正好解释了为什么
隔离组件都是平的而端到端随规模线性增长。改为单条批量语句后（第 12.1 节）30720 档 p99 从
4829ms 降到 511ms（9.5x），p50 从 1111ms 降到 348ms（3.2x）。

## 6. 缺陷：收益递减判据的方向写反了

### 6.1 现象

Reranker 首次接入后检索指标全面变差：四个重排场景的证据数全部塌到 2.0（即 `min_context_k`），
`nDCG@10` 从 0.411 掉到 0.237。同时纯融合链路上 `hybrid-natural` 有 27/32 查询、
`exploratory-natural` 有 28/32 查询也停在 `marginal_gain`，证据只有 3.3 和 5.0 条。

### 6.2 定位过程（含两次被数据否证的推断）

第一次推断：用 6 条手写跨 topic 文档量出 reranker 的相邻相对差值为 0.043~0.145，远高于
`marginal_gain_floor = 0.008`，据此认为阈值对 reranker 过松，并实现了按分数尺度缩放阈值的改动。
用真实候选复测后发现真实的 10 条候选（同 topic 同 facet、仅 depth 不同）相对差值只有
0.00001~0.0024，方向完全相反，该改动已完整回退。

第二次推断：认为融合链路上是"归一化 RRF 的平台期（相邻差值 0.0143~0.0161）低于阈值"。
但 0.0143 > 0.008，按当时的判据不该触发。矛盾说明触发者另有其人。

直接打点 `selectEvidence` 的输入分数，得到 `1.0000, 1.0000, 0.9839, ...`：**前两条分数完全相等**。
两个检索器都把同一文档排在各自第一时，RRF 分数并列，相邻相对差值恰好为 0，
低于任何正阈值，于是必然触发。

### 6.3 根因

判据问的问题是反的：

```
(previousScore - candidate.score) / previousScore < marginal_gain_floor  ->  停止
```

这句话的含义是"下一条**没有明显更差**就停止"。但"没有明显更差"恰恰意味着这条候选和上一条
一样好，应该继续取。两种分数尺度都会落进这个陷阱：

- **融合分数**在两检索器一致命中时并列，差值为 0
- **重排分数**在近重复候选上是平台期，差值 0.00001~0.0024

而真正的断崖是不会看错的：实测 `agreement` 从 2 降到 1 的位置，相邻相对差值为
**0.3896~0.4639**，是平台期噪声（0.0143~0.0161）的 25 倍。

判据改为 `>=`（下跌达到阈值才算断崖），阈值按新语义在两个区间之间重标定
（`fact_lookup` 0.15，`exploratory` 0.30 等，见第 3 节）。余量留得很宽，
因为边界离平台期噪声有 25 倍距离，不需要精细调参。

## 8. halfvec vs fp32 精度损失（真实语料） （归因已被第 17 节修正：fp16 舍入无损，损失全来自 HNSW 近似）

2048 维超出 pgvector `vector` 类型 ANN 索引上限 2000，因此索引必须用 halfvec（上限 4000）。
此前只在退化数据上探过（随机 2048 维向量全聚在 cosine 0.247~0.250），那些数字不可引用。

| 口径 | 值 |
|---|---|
| 生产路径（halfvec + HNSW）chunk 级 recall@10 vs fp32 精确解 | **0.6906** |
| 其中：仅 fp16 舍入造成的损失 | 0.6906 |
| 其中：仅 HNSW 近似造成的损失 | **1**（无损失） |
| top-1 一致率 | 0.7813 |
| Spearman 秩相关（均值 / 最小） | 0.9971 / 0.9646 |
| **topic 级一致率（标注口径）** | **0.875** |

三条结论：

1. **HNSW 近似零损失**（1.000）。chunk 级的差异全部来自 fp16 舍入，与索引无关。
2. **被换掉的文档语义等价**。Spearman 接近 1 说明存活结果的名次几乎未被打乱；
   实测 fp32 精确解 rank10 与 rank11 的距离差为 `2.71e-4`，而 fp16 相对精度约 `4.88e-4`
   ——差距小于精度本身，即这些交换发生在"距离实质相等"的文档之间。
3. **按标注口径影响有限**。topic 级一致率 0.875：32 条查询中 4 条（`shading-loss`、
   `pid-effect`、`encapsulant-yellowing`、`mastery-threshold`）各多出 1 个无关 topic 的 chunk。

延迟代价（同一查询、同一语料）：

| 路径 | p50 | p95 |
|---|---|---|
| halfvec + 索引扫描 | 49.01ms | 76.06ms |
| halfvec + 顺序扫描 | 3.67ms | 4.37ms |
| fp32 + 顺序扫描（精确解） | 64.86ms | 76.29ms |

fp32 精确解慢 60 倍以上。用 0.875 的 topic 级一致率换 60 倍延迟，取舍成立。

## 10. 已知不足

- **`approximate` 向量模式的召回损失只在本语料上标定**（见 12.2）。chunk 级 86.7%、topic 级
  0.875 都来自这套近重复合成语料；换语料必须重测才能决定是否可用。默认仍是 `exact`。
- **nDCG@10 的绝对值不可用于判定达标**（见 13.4）。语料 grade 3 只占相关集 1/4，而 nDCG 的
  分母必须是 grade 降序的最优排序，因此存在约 0.64 的天花板。只能同口径横向比较。
- **真实用户满意度仍未测量**。第 16 节补了一个与裁判独立的标注者（均值 4.375，满意率 84.4%），
  但它与裁判 `completeness` 的相关系数只有 **0.248** —— 两个自动打分器在同一批答案上互相
  印证不了。这本身就说明单一自动指标不足以宣称"用户满意"，需要真实用户或多人盲评。
  n=32、单标注者、非盲评，也都是局限。
- **ANN 索引没有按 `(tenant_id, index_version_id)` 分区**（见 17.1）。5 套语料共用一个 HNSW 图，
  `ef_search` 先取全局近邻再按语料过滤，单套语料的检索延迟因此随库内总行数增长，极端情况下
  会被过滤到 0 行。当前靠 `hnsw.iterative_scan = relaxed_order` 兜住，但正解是分区索引。
- **`hnsw.iterative_scan` 尚未接入产品代码路径**，只在 halfvec 探针里设置。生产检索仍依赖
  `ann_recall_mode = exact`（不走 ANN），所以暂未受影响；一旦启用 `approximate` 就必须一起配。
- **重排的 nDCG 仍低于无重排**（见 6.5），但这是标注口径与重排器判断不一致，不是缺陷。
  要分清两者需要人工标注或第二套标注口径，未做。
- **`score_floor` 在全部 11 个场景中一次未触发**，这条路径仍然缺少实测覆盖。
- **语料是合成的近重复文本**。同 topic 同 facet 仅 depth 不同，这放大了 reranker 分数接近的
  程度。第 6 节的根因（并列与平台期被当成收益递减）在任何语料上都成立，但
  `marginal_gain_floor` 的具体标定值依赖本语料的 gap 分布，换语料需要重新验证。
- **裁判与被评模型是同一个** `Qwen3.5-4B`，存在自我偏好风险。引用精确率（客观口径）作为
  交叉校验，但未与人工标注或第二个模型对比。
- **bigram 命中数下限 2 基于本语料标定**，硬编码而非配置项。
- **单一 embedding 模型**，未做跨模型对比。
- **Agent 单轮墙钟 p99 不可信**（n=60）。
- **只测了 `fact_lookup` 与 `exploratory` 两个 intent 的端到端质量**。其余 5 个 intent 只有
  计划参数（第 3 节），没有质量数据：`count_events` / `comparison` / `multi_hop` / `temporal`
  都要求 `structured_query_required`，需要结构化事件语料才能评。

## 12. 性能优化（保持质量不变）

两项优化，都以"质量指标逐位不变"为前提。优化后重跑全部套件：11 个检索场景的
证据数/nDCG@10/R@10/MRR **与优化前完全一致**，答案质量引用精确率仍为 1.000，
halfvec 精度数据逐位复现，Agent 成功率仍为 100%。

### 12.1 授权复查：逐条往返 → 单条批量语句

`RetrievalGateway` 原先对融合后的每个候选调用一次 `canRead`，即每候选一次数据库往返。
在真实语料上以 24 个候选实测：

| 方式 | 耗时 | 结果 |
|---|---|---|
| 单次 `canRead` | 1.6ms | — |
| 串行 24 次 | **54.7ms** | 24 条放行 |
| `Promise.all` 24 次 | 32.7ms | 24 条放行 |
| 单条 `unnest` 批量语句 | **3.5ms** | 24 条放行（完全一致） |

54.7ms 约占 `fact_lookup` 端到端的 33%。改法是给 `RetrievalAuthorizationPort` 增加**可选**的
`canReadAll`，`PostgresMemoryAuthorization` 用 `unnest` 把候选拼成一张临时表，与
`memory_chunk` 在 **citation 的全部四列**（chunk_id / artifact_id / uri / digest）上连接，
再接 `memory_record`、`retrieval_index_version`，`WHERE` 与单条版本逐字相同。

契约是"**返回被放行的集合**"而非"返回被拒绝的集合"，所以任何遗漏都表现为拒绝而不是放行；
批量语句抛错时网关把整批记为授权失败并回落到原来的串行循环，失败方向仍然是关闭的。
`canReadAll` 缺失时走原逻辑，实现方无需改动。

集成测试断言批量与逐条**结果完全相同**，包括：越权 chunk 必须被拒、篡改 digest 的候选返回
空集、空 purpose 返回空集。快而错的授权比慢而对的更糟，所以这几条是硬断言而非抽查。

### 12.2 向量检索：ANN 下推作为**显式可选项**

原实现把 ACL 谓词与 `ORDER BY ... <=>` 放在同一次扫描里。ACL 跨 `memory_record` 与
`retrieval_index_version` 两张表，形成 `Join Filter`，计划器无法把 ANN 排序下推到基表：
实测 30720 行全部物化后 top-N 排序，**4092ms，HNSW 索引完全没被使用**。

把向量搜索改成先在基表上跑（只带索引自己的谓词），再用 ACL 过滤其输出，可以让 HNSW 生效。
但这条路有代价，实测（30720 chunk，8 查询，top-16，对照 fp32 精确解）：

| 模式 | 召回 | p50 |
|---|---|---|
| `exact`（默认） | **100%** | 129ms |
| `approximate` | 86.7% | ~3ms |

因此它是 `ann_recall_mode` 选项而**不是**默认行为：13% 的 chunk 级召回损失必须由调用方知情
决定，不能由一个隐藏常量替他决定。默认保持 `exact`，即优化前的行为。

过程中有三处推断被数据否证，一并记录：

1. **"ef_search=512 召回 100%，所以 512 是安全默认值"** —— 错。`EXPLAIN` 显示 ef=512 时计划器
   **放弃了索引改走顺序扫描**，"100% 召回"是顺序扫描天然精确，不是 HNSW 变准了。索引路径的
   真实召回上限是 86.7%（ef 64~300 全部相同）。
2. **"下推对 `exact` 也有收益"** —— 错。下推 + 拒绝索引实测 476ms，反而比原写法慢。
   `exact` 因此保留原来的单次扫描。
3. **"halfvec 距离更快"** —— 对纯排序场景是反的。同进程交替实测 10 条查询：
   `vector` + MATERIALIZED CTE **129ms**、`halfvec` + CTE 585ms、`halfvec` 无 CTE 1015ms。
   halfvec 要为每行做 2048 维 fp32→fp16 转换，而该模式已经拒绝了索引，这个转换是白付的。
   `exact` 因此用 `vector` 距离 + `MATERIALIZED` CTE（后者强制 ACL 先过滤，排序只作用于已授权行）。

`approximate` 路径的两个正确性陷阱也都实测过并处理：

- **内层扫描看不到 ACL**，固定倍数会静默少返回：实测内层 LIMIT 16 只剩 13 条可读。改为逐次
  加倍窗口，只在"够数"或"内层返回数 < 允许数（索引已取尽）"时停止。
- **内层必须限定 `index_version_id`**，否则同一张表里其他 logical_name 的行会占满候选窗口：
  未加此限制时 14/32 条查询返回了比精确解更远的文档，标注命中从 256 掉到 192。
  且必须用 `= ANY($1)` 常量数组，写成 `IN (SELECT ...)` 子查询会让计划器再次放弃索引（1268ms vs 5.3ms）。

集成测试断言 `approximate` 下越权 chunk 依然不出现——重排执行顺序不等于放宽授权。

## 13. 评测口径缺陷与语料重构

前 12 节的检索指标有两个口径问题，修正后结论有变化，因此单列一节说明。

### 13.1 Recall@k 的分母写错，与 Precision@k 塌缩成同一个数

原实现是 `命中数 / min(relevantTotal, k)`。分母跟着 k 变，于是当 `relevantTotal >= k` 时
它恒等于 `命中数 / k` —— 那就是 Precision@k 的定义。

实测证据：修正前 **11 个场景 × 3 个 k 值（5/10/20）上 Recall 与 Precision 逐位完全相等**，
两个指标塌缩成一个，其中一个是冗余的。修正为 `命中数 / relevantTotal` 后 0/11 相等。

### 13.2 语料结构让 Recall@k 不可达

修正分母后暴露出更根本的问题：原语料 `depth=240`，每条查询的相关 chunk 是 **960 条**，
而检索只取 10~20 条。真实 Recall@10 因此是 0.0091~0.0104 —— 取 10 条不可能召回 960 条的
10%，**这个指标被语料构造方式锁死，测不出任何差别**。

根因是 `depth` 同时承担了两件互相冲突的事：制造语料体积，和决定相关集大小。

修法是把两者解耦，新增 384 个**干扰 topic**（24 簇 × 16 个，取风力发电/储能电池/配电网等
与光伏相邻但不重叠的领域）。它们有独立的 `cluster_id`，所以 `gradeFor` 对任何真实查询都返回
0 —— 既不是同 topic，也不在同 cluster，纯粹充当检索噪声。体积由它们承担
（`--distractor-depth`），真实 topic 用 `--depth 3`，相关集降到 12 条。

| | 旧语料 | 新语料 |
|---|---|---|
| 总 chunk | 30720 | 31104 |
| 每查询相关 chunk | 960 | **12** |
| Recall@10 理论上限 | 0.01 | **0.83** |
| Recall@20 理论上限 | 0.02 | **1.00** |

检索器层实测（31104 chunk，32 查询）：

| 检索路径 | MRR | nDCG@10 | P@10 | R@10 | R@20 | facet@10 | 零结果 |
|---|---|---|---|---|---|---|---|
| vector（自然句） | 1.000 | 0.854 | 1.000 | **0.833** | **1.000** | **1.000** | 0 |
| lexical（分词） | 1.000 | 0.854 | 1.000 | **0.833** | **1.000** | **1.000** | 0 |
| vector（分词） | 1.000 | 0.829 | 1.000 | **0.833** | **1.000** | **1.000** | 0 |
| lexical（自然句） | 0.875 | 0.771 | 0.853 | 0.711 | 0.852 | 0.852 | 4 |

`0.833 = 10/12`，即三条路径都打到了 Recall@10 的理论上限；R@20 与 facet 覆盖率均为 1.000。

### 13.3 新增 facet 覆盖率

本语料同一个 `(topic, facet)` 有多条只差 `depth` 的近重复，信息上是同一份。按 chunk 计召回时
「命中 10 条近重复」与「命中 10 个不同角度」得分相同，测不出取回了几个角度。因此在
`(topic, facet)` 粒度上另计一次覆盖率，分母是该 topic 的 4 个 facet。

### 13.4 nDCG 的理想序列改错过一次

曾把理想序列从「grade 降序」改成「按语料密度交错」（每 4 条放 1 条 grade 3），动机是让分母
可达。**结果 nDCG 冲到 1.310** —— 大于 1 自相矛盾：检索器把 definition 集中排在最前时，
实际 DCG 会超过交错序列的 DCG。

根因是把「可达性」与「最优性」搞混了。nDCG 的分母必须是**最优**排序，而按 grade 降序永远优于
任何交错排列，所以只有降序是合法分母。已改回标准定义。

由此保留一个必须如实说明的局限：本语料 grade 3（definition）只占相关集的 1/4，而理想 top-10
全是 grade 3，所以 **nDCG@10 的绝对值存在远低于 1 的天花板（facet 均匀分布时约 0.64），
不能用于判定"是否达标"**，只能用于同口径的横向比较。要让它的绝对值有意义，需要改语料的
grade 分布，而不是改分母。

## 14. HyDE：作为零结果兜底，而不是查询预处理

`lexical` 路径在自然整句下有 4/32 查询零结果（`斜射光损失为什么更大`、`PID 是什么条件下发生的`、
`热斑是怎么形成的`、`PR 值是什么意思`）。成因是 CJK bigram 要求至少命中 2 个 bigram，
极短中文问句凑不出来 —— 那个下限本身是为了防止单个跨词边界巧合导致 10 条全错。

先量化了**全局** HyDE（每条查询都改写）：

| 路径 | P@10 | MRR | facet@10 | 零结果 |
|---|---|---|---|---|
| lexical 原始 | 0.875 | 0.875 | 0.219 | 4 |
| lexical + 全局 HyDE | 0.750 | 0.750 | 0.188 | **0** |
| vector 原始 | 1.000 | 1.000 | 0.367 | 0 |
| vector + 全局 HyDE | 0.969 | 0.969 | **0.414** | 0 |

零结果确实修好了，但 lexical 的 P@10 与 MRR 各降 **14%**，且每条查询多一次模型调用
（+958ms p50、+104 token，而端到端预算只有 401ms）。**用另外 28 条查询的 14% 精度换 4 条的
召回缺口是坏交易**，所以没有做成预处理。

改为 `QueryRewritePort`，**仅当所有检索器都返回 0 条时**触发；若改写后仍无结果则丢弃改写、
保留原本的空结果：

| lexical 自然句 | 无 HyDE | 零结果兜底 |
|---|---|---|
| 空结果 | 4 | **0** |
| MRR | 0.875 | **0.906** |
| P@10 | 0.525 | **0.544** |
| facet@10 | 0.219 | **0.227** |
| 触发改写次数 | 0 | **4** |
| p50 | 125ms | 144ms |
| p95 | 216ms | 1892ms |

`-14%` 变成 `+3.6%`，且代价集中在真正需要的 4 条查询上（p95 抬高只反映那 4 条）。

四条不变量都有单元测试覆盖：

1. 检索成功时**绝不**调用改写器（否则白付一次模型调用）。
2. 改写后仍无结果时丢弃改写，空结果保持原样。
3. 改写器抛错不能把空结果升级成检索失败 —— 空结果本身是一个诚实的答案。
4. `trace.rewritten_query` 只在改写真正救回结果时出现。调用方必须能分辨证据回答的是
   原问题还是机器改写后的问题；`EvidencePackTrace` 因此扩了这个可选字段
   （schema 是 `additionalProperties: false`，不能偷偷塞）。

## 15. 三层评测：检索 / 生成 / 端到端 + token 成本

此前只有检索层有时延，生成层只有质量分而没有时延与 token，端到端没有合并口径。现已补齐
（新语料，32 查询，`fact_lookup`）：

| 层 | n | p50 | p95 | p99 |
|---|---|---|---|---|
| 检索 | 32 | 377ms（32%） | 488ms | 516ms |
| 生成 | 32 | 801ms（67%） | 1211ms | 1298ms |
| **端到端** | 32 | **1191ms** | 1649ms | 1699ms |
| 裁判（仅评测开销） | 32 | 877ms | 1287ms | 1337ms |

裁判调用**不计入端到端**：它是评测装置的成本，算进去会让被测系统看起来慢一倍。

token 成本：

| 项 | 值 |
|---|---|
| 生成调用 | 32 次 |
| 输入 | 30200 token（**96.9%**） |
| 输出 | 968 token（3.1%） |
| 每查询 | **974 token** |
| 裁判开销（不计入系统成本） | 35347 token |

**输入占 96.9%**，每查询 944 个输入 token 对应 5.9 条证据，约 160 token/条。这说明 RAG 的
token 成本几乎完全由证据量决定，而不是由答案长度决定 —— 想降成本要减证据条数或压缩证据，
调 `max_output_tokens` 没有意义。这也解释了第 12 节为什么把证据数从 5.8 提到 12.9 会让
token 翻倍。

生成层质量（新语料）：判定 32/32，faithfulness 4.906、relevance 4.875、completeness 4.438、
**引用精确率 1.000**、平均证据 5.9 条。

`p99` 在 n=32 下不可信，已按同一口径标注 `p99_reliable: false`。

## 16. 用户满意度：独立标注，以及它与 LLM 裁判的分歧

第 15 节的 faithfulness / relevance / completeness 由 `Qwen3.5-4B` 打分，而被测模型也是它，
存在自我偏好风险。本节由**另一个标注者**（Claude，与被测/裁判模型相互独立）逐条阅读全部 32 条
的「问题 + 证据 + 答案」后打分，口径是**用户拿到这个答案是否满意**，而不是是否忠于证据：

| 分 | 判据 |
|---|---|
| 5 | 直接回答问题，无错误、无冗余、无需再查 |
| 4 | 正确，但有小瑕疵（措辞生硬、轻微冗余、混入元信息） |
| 3 | 正确但明显不完整，或掺入无意义文本 |
| 2 | 只答了一部分，用户仍需自己再查 |
| 1 | 答非所问，或含错误信息 |
| 0 | 完全不可用 |

结果（n=32）：**均值 4.375**，分布 `5分:19 / 4分:8 / 3分:3 / 2分:2`，**满意率（>=4）84.4%**。
逐条分数与理由记录在评测产物 `.sat-v2.json` 里 —— 打过分的内容必须可复核，因此 `per_query`
同时保存了问题、答案原文与证据摘要。

### 16.1 最重要的发现：两个打分者几乎不相关

裁判的 `completeness` 与本节满意度的 **Pearson r = 0.248**。32 条里 20 条一致、8 条裁判更松、
4 条裁判更严，其中 5 条分歧达到或超过 2 分：

| 查询 | 裁判 C | 满意度 | 分歧原因 |
|---|---|---|---|
| `q.shading-loss` | **0** | **5** | 答案「整串输出下降超过三分之一」直接对题；裁判称「证据全是错误的章节标题描述」，但证据里确有该事实 |
| `q.mismatch-loss` | **1** | **5** | 裁判要求「阴影、老化等具体成因」，那些**不在证据里**，属于对世界知识的期待 |
| `q.formative-assessment` | 0 | 3 | 双方都认定证据只有形成性一侧；裁判判 0，但「诚实说明缺口」对用户仍有部分价值 |
| `q.row-spacing` | **5** | **2** | 答案混入「关于车内具体数值」——光伏语境下是无意义文本，裁判却称其「明确区分了车辆场景」 |
| `q.mastery-threshold` | 3 | **2** | 答案基本在复述 facet 模板措辞，没真正回答如何设定阈值 |

**方向不是单一的偏松或偏严，而是判据不同**：裁判倾向于用「证据是否覆盖了它认为该有的信息」
打分，甚至为答案里的语病编造合理解释（`q.row-spacing` 那条尤其明显）；满意度口径只问
「用户拿到这个答案够不够用」。

### 16.2 一个客观旁证

引用精确率恒为 1.000、无方差，无法用来仲裁两个打分者。但有一个客观可检测的信号：答案是否
**照搬了语料的 facet 模板措辞**（如「结合实测数据与误差范围」「将可观测指标与结论连接」）。
这类答案是在复述生成模板而非回答问题。实测 3/32 条命中，且**这 3 条本节给的分都低于裁判**
（4/2/4 对 5/3/5）。样本太少不足以定论，但方向一致。

### 16.3 必须说明的局限

- **n=32，且只有一个独立标注者**。没有第二人复核，无法计算标注者间一致性（Cohen's kappa），
  所以本节分数同样不是"真值",只是一个与裁判独立的第二意见。
- **标注者知道自己在评测什么**，非盲评，存在确认偏差。
- **真实用户满意度仍未测量**。本节与第 15 节都是模型/AI 的判断，都不能代替真实用户。r = 0.248
  这个数字本身就是证据：**两个自动打分器在同一批答案上都难以互相印证，说明任何单一自动指标
  都不足以宣称"用户满意"**。

## 17. 新语料下的全套复测（halfvec / 规模曲线 / Agent）

第 13 节换语料后，其余三套必须重跑才能与检索层放进同一张表。复测过程中查出两个探针缺陷和
一个产品缺陷，因此三组数字都有变化。

### 17.1 halfvec 探针有两个缺陷，归因反了

`recall_vs_exact` 第一次跑出 **0.0187**。这个数量级不可能是精度损失，查下去是两个独立缺陷：

**缺陷一：`SET LOCAL` 在事务外是静默空操作。** 探针在事务外发
`SET LOCAL enable_indexscan = off`，PostgreSQL 接受语句但立刻丢弃设置
（`SHOW enable_indexscan` 仍是 `on`）。三条本该不同的路径跑的是同一个计划，
"fp16 舍入损失"与"HNSW 近似损失"从来没被分开过。

**缺陷二：ANN 索引没有按语料分区。** `memory_chunk_embedding_ann_idx` 的谓词只有
`embedding IS NOT NULL AND chunk_level = 'child'`，本库 5 套语料共 86784 行都在同一个 HNSW 图里。
`ef_search=40` 先取全局最近的约 40 行，再由 `Filter: index_version_id = ...` 逐行剔除。
执行计划显示新语料被剔到 0 行（`Rows Removed by Filter: 40`）。开启
`hnsw.iterative_scan = relaxed_order`（pgvector 0.8.6 提供，默认 `off`）后恢复正常。

修好后归因**与之前发布的结论相反**：

| | 旧（坏探针） | 新（已修） | 含义 |
|---|---|---|---|
| fp16 舍入损失 recall | 0.6906 | **1.0000** | fp16 完全无损 |
| HNSW 近似损失 recall | 1.0000 | **0.8156** | 损失全部来自 ANN 近似 |
| topic 级一致率 | 0.8750 | 0.8438 | RAG 实际关心的口径，基本持平 |
| spearman 均值 | 0.9971 | 0.9944 | 排序几乎不变 |

**之前把 HNSW 的近似损失记在了 fp16 头上。** 结论因此要改：降到 fp16 存储不损失精度，
真正需要权衡的是 ANN 召回率，也就是第 12.2 节 `ann_recall_mode` 那个决定。

### 17.2 规模曲线：旧结论是伪影，质量其实持平

旧曲线显示 1920 → 30720 时 nDCG@10 从 0.462 升到 0.582，读起来像"语料越大质量越好"。
那是伪影：旧语料放大规模时每条查询的相关 chunk 也同步变多，分母与可命中目标一起膨胀，
测的是标注密度而不是检索能力。

新口径固定相关集为 12，只改干扰量（`hybrid-natural`）：

| 语料量 | nDCG@10 | R@10 | R@20 | facet@10 | MRR | p50 | p99 |
|---|---|---|---|---|---|---|---|
| 1920 | 0.680 | 0.492 | 0.492 | 0.828 | 1.000 | 384ms | 1360ms |
| 8064 | 0.687 | 0.492 | 0.492 | 0.820 | 1.000 | 372ms | 504ms |
| 15744 | 0.687 | 0.492 | 0.492 | 0.820 | 1.000 | 384ms | 468ms |
| 31104 | 0.687 | 0.492 | 0.492 | 0.820 | 1.000 | 563ms | 1885ms |

**16 倍语料增长下检索质量完全持平**，R@10 与 facet 覆盖率一位不差。这比"越大越好"是更强的
结论，也更可信。延迟在 31104 档抬高，与 17.1 的发现一致：ANN 索引跨 5 套语料共 86784 行，
过滤代价随库内总量而非单套语料增长。

### 17.3 Agent：查出一个真实契约缺陷

复测第一轮 **60/60 全部失败**，`failure_reasons` 只有 `start:TypeError` 一项。不是评测装置的
问题，是产品缺陷：

三个 Agent 都用 `${model.snapshots.model}|${model.snapshots.routing}` 记录来源，好让结果能同时
追溯到模型构建与选中它的路由表。这个拼接值是 **187 字符且含 `|`**，而 `ExecutionSnapshots.model`
声明为 `Identifier`（上限 160 字符，字符类不含 `|`）—— 两条都违反。`experience-engineer` 的
`tools` 同样拼接，同样违反。

于是**每一次模型驱动的运行都在租约取得之后、契约校验处失败**，而且只暴露成 `start:TypeError`，
看不出是校验问题。这个缺陷在此前所有 Agent 数据里都存在，只是之前没跑到这条路径。

修法是新增 `CompositeSnapshot` 类型（上限 512，字符类加入 `|`）而**不是**放宽 `Identifier`——
后者在 112 处被引用，放宽会削弱全局校验。同时保留对空白与控制字符的拒绝，因为这些值要进审计
账本，不能变成自由文本字段。两个回归测试覆盖：拼接值必须通过，含空格/换行/前导分隔符必须拒绝。

修好后（`--rounds 60 --concurrency 1,4,8,12 --min-calls-per-level 100`）：

| 阶段 | 成功率 | 调用数 | 失败 | 重试 | p50 | p95 | p99 | p99 可信 |
|---|---|---|---|---|---|---|---|---|
| 顺序 | **60/60** | 120 | 0 | 0 | 2528ms | 3308ms | 3640ms | 是 |
| 并发 1 | 50/50 | 100 | 0 | 0 | — | — | 3400ms | 是 |
| 并发 4 | 52/52 | 104 | 0 | 0 | — | — | 4670ms | 是 |
| 并发 8 | 56/56 | 112 | 0 | 0 | — | — | 4636ms | 是 |
| 并发 12 | 60/60 | 120 | 0 | 0 | — | — | 5854ms | 是 |

契约违规 0，传输失败 0，全部 p99 满足 n>=100 的可信门槛。

## 18. 提升 R@10：瓶颈不在检索，在选择窗口

第 13 节把 Recall@k 变成可达之后，证据层 R@10 停在 0.492，而检索器层是 0.833。差距 41% 全部
发生在检索之后。

### 18.1 先证明检索侧没有损失

按 `candidate_k` 扫描 lexical ∪ vector 的并集，统计其中含多少条相关 chunk（相关集 12）：

| candidate_k | lexical 返回 | vector 返回 | 并集 | 并集内相关命中 | 噪声 |
|---|---|---|---|---|---|
| 16 | 11.0 | 16.0 | 16.7 | **12.0 / 12** | 4.7 |
| 24 | 12.0 | 24.0 | 25.2 | 12.0 / 12 | 13.2 |
| 32 | 12.8 | 32.0 | 33.5 | 12.0 / 12 | 21.5 |
| 64 | 14.8 | 64.0 | 66.8 | 12.0 / 12 | 54.8 |

`candidate_k = 16` 时并集里**已经含有全部 12 条相关 chunk**。加到 64 只让并集从 16.7 涨到 66.8，
相关命中一条不增，全是噪声。**检索器从来不是瓶颈，加大召回窗口对 R@10 完全无效。**

### 18.2 真正的上限是算术

证据层 Recall@10 受 `min(context_k, relevant_total) / relevant_total` 约束：

| context_k | 6 | 8 | 10 | 12 |
|---|---|---|---|---|
| R@10 理论上限 | **0.500** | 0.667 | 0.833 | 1.000 |

`fact_lookup` 的 `context_k = 6` 把上限锁在 0.500，实测 0.492 —— **已经贴着上限，不是检索质量问题**。

### 18.3 扫描选择窗口，找到拐点

| context_k | rerank_k | 证据数 | R@10 | facet@10 | 引用精确率 |
|---|---|---|---|---|---|
| 6 | 10 | 5.9 | 0.492 | 0.820 | **1.000** |
| **11** | **18** | **10.1** | **0.794** | **0.977** | **0.991** |
| 14 | 24 | 10.8 | 0.794 | 0.977 | 0.955 |
| 17 | 29 | 11.4 | 0.794 | 0.977 | 0.930 |

R@10 在 **0.794 处饱和**（k=10 的理论上限是 10/12 = 0.833，已达其 95%），而引用精确率在越过
相关集大小后单调下降 —— 窗口一旦超过 12，多出的每个位置只能由非相关 chunk 填充。

`11 / 18` 正好在拐点：**R@10 +61%、facet 覆盖 +19%，引用精确率只降 0.9%**。因此 `fact_lookup`
的默认值从 `context_k 6 / rerank_k 10 / candidate_k 16 / fusion_k 24` 改为 `11 / 18 / 24 / 36`。

### 18.4 全场景复测结果

| 场景 | R@10 前 → 后 | facet@10 前 → 后 | 证据数 | p50 |
|---|---|---|---|---|
| hybrid-natural | 0.492 → **0.794** (+61%) | 0.820 → 0.977 | 5.9 → 10.1 | 563 → 508ms |
| hybrid-tokenized | 0.500 → **0.823** (+65%) | 0.844 → **1.000** | 6.0 → 10.6 | 559 → 536ms |
| vector-only-natural | 0.500 → **0.815** (+63%) | 0.852 → **1.000** | 6.0 → 11.0 | 549 → 522ms |
| lexical-only-natural | 0.430 → **0.685** (+59%) | 0.734 → 0.852 | 5.3 → 8.9 | 95 → 7ms |
| lexical-only-tokenized | 0.500 → **0.799** (+60%) | 0.914 → **1.000** | 6.0 → 10.1 | 91 → 6ms |
| hybrid-natural-rerank | 0.500 → **0.810** (+62%) | 0.859 → **1.000** | 6.0 → 10.4 | 713 → 672ms |
| vector-only-natural-rerank | 0.500 → **0.810** (+62%) | 0.859 → **1.000** | 6.0 → 10.4 | 736 → 727ms |

`exploratory` 各档不变（它的 `context_k` 本来就在拐点之上）。延迟没有变差，多数略降。

lexical 的 91ms → 7ms 不是优化效果：`--repeats 2` 的第二遍命中 PostgreSQL 缓存，同一次运行的
p95 仍是 141ms。这里只应读质量列。

### 18.5 生成层的连带变化

| | context_k=6 | context_k=11 |
|---|---|---|
| faithfulness | 4.938 | **5.000** |
| relevance | 4.844 | **5.000** |
| completeness | 4.250 | **4.875** |
| 引用精确率 | 1.000 | 0.991 |
| token/查询 | 972 | 1552 (+60%) |
| 端到端 p50 | 1129ms | 1377ms |

三项裁判评分全部上升，代价是 **token +60%、端到端 +22%**。这与第 15 节的结论一致：token 成本
由证据量决定，所以提高 R@10 必然要按比例付 token。这是一个明确的取舍，不是免费收益。

### 18.6 顺带修正：`score_floor` 首次被触发

第 12 节记录 `score_floor` 在 352 次选择中触发 0 次。窗口放宽后，`fact_lookup` 在
`context_k = 11` 档出现了 2 次 `score_floor` 停止。此前"永不触发"的原因确认是
`context_k` 太小、选择在降到该分数之前就已停止，与分数尺度无关。

## 19. 自适应 context_k：实现了，测出来是负收益，因此默认关闭

第 18 节把 `context_k` 从 6 调到 11 之后，R@10 在 0.794 饱和。但那是**相关集恒为 12 条**的语料，
固定 `context_k` 在每条查询上都接近最优 —— 这种语料结构上自适应策略最好也只能打平。

### 19.1 先造能测出差别的语料

新增 `--vary-relevant-sets`：真实 topic 的 depth 按序号乘 `[1,1,2,4,8,1,3,6]`，使每条查询的相关集
变成 **12~96 条**（均值 39），语料总量 31968 chunk 基本不变。倍数按序号轮转、与主题内容无关，
避免"某类主题恰好稀疏"成为混淆变量。

这样固定 k 必然两头都错：相关集 12 条时取 11 条已接近极限，相关集 96 条时取 11 条必然漏掉 85 条。

### 19.2 机制：第四道停止闸

现有三道闸没有一道在问"下一条还相关吗"：`context_k` 只问数量，`score_floor` 问绝对分（RRF 归一化
后几乎不触发），`marginal_gain_floor` 只比较**相邻**两条。

`marginal_gain_floor` 有一个可复现的盲区：**缓慢单调衰减**。构造分数每档衰减 8% 的候选表，每一步
落差都远低于 0.15 的阈值，于是选择一路取到 `context_k = 11`，最后一条只值首条的 **43%**，
`marginal_gain` 全程未触发。

新增 `relative_floor`：与**本次查询最好的那条**比较，而不是与前一条比。这个比较不会在每次接受
候选后重置，因此能看见累积衰减。加入后同一组构造数据停在相对首条 85% 处，断崖情形不受影响。

### 19.3 实测结果：负收益

在 12~96 不均匀语料上，同一批候选、唯一变量是 `relative_floor`：

| relative_floor | 证据数 | R@10 | facet@10 | 引用精确率 |
|---|---|---|---|---|
| **0（关闭）** | 9.8 | **0.909** | **0.758** | 0.994 |
| 0.84 | 9.4 | 0.894 | 0.734 | **1.000** |

**用 1.7% 的召回和 3.2% 的 facet 覆盖，换了 0.6% 的引用精确率。** 对"提升 R@10"这个目标，
方向是错的。因此七个 intent 的 `relative_floor` 全部默认为 0，机制保留但不启用。

### 19.4 定标错误：用结果反推门槛是循环论证

0.84 这个值来自**已选证据**的 `score/best` 分布（相关候选 5 分位 0.872、不相关 95 分位 0.836，
两者几乎不重叠，看起来是干净的分界）。

但这道闸运行在**候选窗口**上，而候选窗口里相关候选的 5 分位只有 **0.495**。已选证据本身就是选择器
留下的高分子集，拿它的分布去给筛选前的候选定阈值，等于用结果反推门槛。0.84 因此砍掉了
**30.4% 的相关候选**，这就是 R@10 下降的全部原因。

按候选窗口重新定标后，没有任何单一比例阈值是划算的：

| 阈值 | 保留相关 | 误留不相关 |
|---|---|---|
| 0.50 | 94.0% | 23.7% |
| 0.84 | 69.6% | 3.9% |

两类分布在 0.4~0.5 区间重叠。**要让这个机制有用，需要的不是"占最高分的比例"这种信号** ——
而是绝对的重排相关度，或者对"本次查询大约有多少条相关文档"的估计。

### 19.5 当前配置在不均匀语料上的表现

R@10 的绝对值不能与第 18 节比较：那里相关集恒为 12（上限 10/12 = 0.833），这里相关集 12~96
（加权上限 **0.456**）。同口径应看"达上限百分比"：

| 场景 | R@10 | 达理论上限 |
|---|---|---|
| hybrid-tokenized | 0.449 | **99%** |
| vector-only-natural | 0.453 | **99%** |
| hybrid-natural-rerank | 0.451 | **99%** |
| exploratory-tokenized | 0.453 | **99%** |
| lexical-only-tokenized | 0.445 | 98% |
| hybrid-natural | 0.438 | 96% |
| lexical-only-natural | 0.397 | 87%（4 条 CJK 零结果所致） |

**96~99% 已经贴着算术天花板。** 结论是：在这套语料上 R@10 没有剩余空间，除 `lexical` 自然句那条
路径以外（第 14 节的零结果兜底已把它从 4 条降到 0，但该场景本身不启用兜底）。

## 20. 真实文档语料：合成语料掩盖了两个产品缺陷（第三个见 21.4；本节 R@10 的 gold set 定义有误，已由第 22 节修正）

前 19 节全部跑在合成语料上。它的 chunk 是 `(topic, facet, depth)` 三维构造出来的近重复段落，
能让 Recall 可算，但分数分布、术语多样性、entity_keys 结构都不像真实文本。换真实文档重跑后，
**测出两个此前完全看不到的产品缺陷**，修完 R@10 提升近 4 倍。

### 20.1 语料与标注

本机无外网（GitHub 不可达，PyPI 可达），无法下载公开基准，因此用仓库内真实 Markdown：
**5432 chunk / 2.9 MB**，含 64 个项目自有文档与 301 个依赖文档（openai、anthropic-ai/sdk、
exceljs 等的 README 与 CHANGELOG），中英混排，人类撰写。

真实文档没有相关性标签，而 R@10 必须有。三种来源里选了第三种：

| 来源 | 取舍 |
|---|---|
| 人工标注 | 最可信，但 103 查询 × 5432 chunk 无法穷举 |
| LLM 判断 | 裁判与被测同模型，且第 16 节已测出裁判与独立标注者 r = 0.248 |
| **结构化弱标注** | 用文件路径推导，客观、可复核、无模型参与 |

标注粒度试了两种。**包级**（一个 npm 包算一个 topic）不可用：`pkg:openai` 有 847 chunk，取 10 条
最多覆盖 1.2%，`pkg:dayjs` 的 P@10 已经是 1.00 却仍只有 R@10 = 0.018 —— 这时 Recall 衡量的是标注
宽窄，不是检索质量。改用**文件级**（一个 Markdown 文件算一个 topic），相关集 8~58，
R@10 加权上限 **0.6505**，103 条查询。

标注的**已知偏差**必须写明：它假设同一文件的所有 chunk 都与该文件的查询相关，因此 Recall 偏高；
跨文件讲同一概念的段落被判为不相关，方向相反。两个偏差不能假设互相抵消，绝对值只用于与合成语料
对照，不作为达标依据。

### 20.2 缺陷一：英文自然句在词法检索上必然零结果

`websearch_to_tsquery('simple', ...)` 把所有词 AND 连接，而 `simple` 配置既不做词干化也不去停用词：

```
'what does the adr document specify'
  -> 'what' & 'does' & 'the' & 'adr' & 'document' & 'specify'
```

要命中必须六个词全部出现在同一 chunk。实测该 tsquery 返回 **0 行**，而单独的 `adr` 返回 47 行。
后果是 **96/96 条自然句查询全部零结果**，`lexical-only-natural` 的 MRR 与 R@10 都是 0，
且 hybrid 静默退化成 vector-only —— 两者逐查询完全相同，96/96 一致。

合成语料测不到这点：它的自然句查询是中文，走 CJK bigram 路径（第 14 节已用 OR 修过）。
**英文整句在 simple 配置下必然全零,只有真实英文文档能暴露。**

修法与 CJK 侧同口径：Latin 词也走 OR + 最小命中数。AND 语义仍是主路（全词命中通过
`query.value` 得最高分），OR 只把部分命中托到零以上，权重 0.5 保证不越过全词命中。
停用词表按文档频率定：`the` 命中 41.9% 的 chunk，而同一查询里的实词都低于 1%，区分度明确。
门槛取 2 个实词，与 CJK 的 bigram 门槛一致——单个实词命中常是巧合（`document` 出现在 0.8% 的
无关包里）。

| 场景 | MRR 前→后 | 零结果 前→后 |
|---|---|---|
| lexical-only-natural | 0.000 → **0.724** | 96 → 2 |
| lexical-only-tokenized | 0.742 → 0.758 | 6 → 2 |

### 20.3 缺陷二：证据层把同一文件的段落当成重复证据丢弃

修完缺陷一后 R@10 仍只有理论上限的 8~9%，而 MRR 0.73 说明排序头部是准的。这个矛盾指向证据层。

`selectEvidence` 的去重规则原本是：**候选若不引入新 `entity_key`、且与首条 `source_type` 相同，
就丢弃**。这等价于"每个来源只留 1 条"。

合成语料从不触发它，因为那里每个 chunk 都带 `facet.fN` 与 `depth.N`，条条都有新 key。真实文档
没有这种构造维度：同一个 Markdown 文件切出的 chunk 共享 `[topic.<文件>, source.<文件>]`，
`source_type` 又全是 `text/markdown`，于是**第 2 条起全部被当成冗余**。

实测 `big-integer/README.md`（58 chunk）：检索层已把 **11 条正确 chunk 排进前 20**，证据层只交出
**5 条、其中相关 1 条**，`stop_reason` 是 `exhausted`。

改成可配置的 `max_chunks_per_source`，保留"不让单一来源灌满整包"的原意，但上限不再是 1。定标：

| 上限 | R@10 | 达上限 | 引用精确率 | tokens |
|---|---|---|---|---|
| 1（原行为） | 0.054 | 8% | 0.232 | 685 |
| 4 | 0.164 | 25% | 0.451 | 947 |
| **8（采用）** | **0.202** | **32%** | **0.480** | 1054 |
| 11 | 0.204 | 33% | 0.482 | 1071 |

**判据是召回与引用精确率同向上升**：若丢掉的是噪声，放宽上限应当拉低精确率。8 之后饱和
（8→11 只多 0.002 召回），且 11 已越过 `context_k = 11`，等于取消单来源限制。故取 8。

### 20.4 真实语料最终结果

| 场景 | MRR | R@10 | 达上限 | P@10 | nDCG@10 | 证据 | 零结果 | p50 |
|---|---|---|---|---|---|---|---|---|
| **vector-only-natural** | **0.725** | **0.274** | **43%** | 0.418 | **0.475** | 10.9 | 0 | 343ms |
| hybrid-natural-rerank | 0.728 | 0.273 | 42% | 0.416 | 0.474 | 10.9 | 0 | 565ms |
| hybrid-natural | 0.676 | 0.202 | 32% | **0.484** | 0.394 | 7.5 | 0 | 351ms |
| lexical-only-tokenized | 0.589 | 0.192 | 31% | 0.430 | 0.359 | 7.7 | 10 | 6ms |
| lexical-only-natural | 0.570 | 0.188 | 30% | 0.423 | 0.349 | 7.7 | 10 | 8ms |

真实语料上 **vector-only 反超 hybrid**（43% vs 32%）：词法腿在真实文档上引入的噪声多于贡献，
这与合成语料的结论相反（那里 hybrid 与 vector 基本持平）。重排对 vector-only 无增益
（0.274 → 0.273）却多花 222ms。

### 20.5 合成语料回归：同一修复也提升了它

`max_chunks_per_source` 的改动在合成语料上没有退步，反而普遍提升，**8 个场景达到 0.833 的算术
上限、P@10 = 1.000**：

| 场景 | R@10 前→后 | P@10 前→后 |
|---|---|---|
| hybrid-natural | 0.794 → 0.815 | 0.953 → 0.978 |
| lexical-only-natural | 0.685 → **0.763** | 0.822 → 0.916 |
| vector-only-natural | 0.815 → **0.833**（=上限） | 0.978 → **1.000** |
| hybrid-tokenized-rerank | 0.797 → **0.833**（=上限） | 0.956 → **1.000** |

### 20.6 relative_floor 在真实语料上被更强地否证

第 19 节在合成语料上测出 `relative_floor` 是负收益。真实语料给出更硬的证据 —— 候选窗口里
`score/best` 的两个分布**几乎完全重合**：

| | p05 | p50 | n |
|---|---|---|---|
| 相关候选 | 0.436 | 0.520 | 763 |
| 不相关候选 | 0.412 | 0.492 | 965 |

合成语料上至少还有 0.495 vs 0.42 的间隔，真实语料连这点间隔都没有。**RRF 归一化后的分数比不携带
相关性信息**，任何阈值都只是无差别砍证据：0 → 0.9 使证据数 5.0 → 2.6，R@10 单调下降。
默认关闭是对的。

### 20.7 评测脚本自身的两个缺陷（已修）

必须记下来，因为它们一度让结论指向错误方向：

1. **scope 被剥离**：`pkg:@anthropic-ai/sdk` 生成的查询是 `"how do I use sdk"`，返回的是 `openai`
   与某个 ADR 的 chunk，P@10 = 0 对着 473 条相关集。96 条查询里 16 条受影响。
2. **同名查询**：文件级粒度下 5 条查询文本重复，同一次检索对一个 topic 是正确答案、对另一个就是
   错误答案，Recall 与 Precision 都失去意义。已过滤，103 条中保留唯一的。

另有两个实现约束值得记：`chunk_digest` 必须是 `sha256(content)` 本身（索引器会校验，掺入路径会
失败，这是防内容替换的完整性检查）；真实路径含中文与空格，`entity_key` 与 `artifact_id` 都受
`^[A-Za-z0-9][A-Za-z0-9._:@/-]*$` 约束，需可逆编码后再入库，播种与评测必须共用同一份 `safeKey`
实现——曾各写一份，评测侧漏了编码，导致全部查询判成零命中。

## 21. known-item：不依赖标注的检索能力口径（本节引用的 43% 基于错误的 gold set 定义，见第 22 节）

第 20 节的 R@10 只到理论上限的 43%，容易被读成"检索只有四成能力"。为了把"检索链路能力"与
"标注宽度"分开，加了一个不需要任何相关性标注的口径。

### 21.1 方法

把某个 chunk 的原文当查询，看检索能否找回它自己。**正确答案唯一且客观**，不需要任何人判断
"相关"。等距抽样 120 个 chunk（同一语料每次跑出同一批，数字可比），三档查询长度。

它测的是 embedding、索引、ANN、过滤这条链路能不能把一段已知文本找回来。

### 21.2 结果

| 查询长度 | 检索器 | R@1 | R@10 | R@20 | MRR | 未找到 |
|---|---|---|---|---|---|---|
| 300 字 | **vector** | **0.908** | **1.000** | 1.000 | **0.933** | 0 |
| 300 字 | lexical | 0.683 | 0.833 | 0.933 | 0.741 | 8 |
| 120 字 | vector | 0.867 | 0.975 | 0.983 | 0.899 | 2 |
| 120 字 | lexical | 0.592 | 0.808 | 0.925 | 0.663 | 9 |
| 60 字 | vector | 0.708 | 0.925 | 0.942 | 0.789 | 7 |
| 60 字 | lexical | 0.617 | 0.900 | 0.950 | 0.716 | 6 |

向量检索在 300 字查询下 **前 10 召回 100%、91% 直接排第一**。查询信息量下降时 R@1 从 0.908 掉到
0.708，但 R@10 仍在 0.925 以上 —— 短查询主要影响排在第几，不影响能否找到。

### 21.3 这个口径的边界

**它是上界，不是日常表现。** 整段原文当查询比真实用户的短问句容易得多，所以不能拿 1.000 去宣称
检索质量。它的用途是**归因**：

- known-item 100% 而带标注只有 43% → 差距归因于标注宽度
- 若 known-item 也低 → 检索链路真的有问题

两个口径必须并读。单看 43% 会误判成检索缺陷，单看 100% 会高估实际表现。

### 21.4 顺带测出的健壮性缺陷

第一次运行 known-item 直接崩了：`tsquery stack too small`。定位到 exceljs README 的一段 Markdown
表格——独立的 `-` 被 `websearch_to_tsquery` 解析成 NOT 操作符（`a - b` 得到 `'a' & !'b'`），
表格分隔行 `| ---- | ---- |` 连续压入几十个操作符直到解析栈溢出。

这是 PostgreSQL 既有行为，实测 `websearch_to_tsquery('simple', repeat('- ', 60))` 单独就报错，
与本仓库改动无关。但后果是**整次检索抛异常而不是降级返回**。已加 `sanitizeTsQueryText`：压缩连续
的 `-`/`|` 与被空白包围的单个 `-`，但保留词内连字符（`client-s3`、`sha256-js` 这类包名依赖它）。

## 22. gold set 定义错误：R@10 被压到真实值的 39%

第 20、21 节的 R@10 数字全部基于错误的 gold set 定义，本节修正。**公式没错，分母的内容错了。**

### 22.1 错在哪

`Recall@k = 前 k 条里的命中数 / gold set 大小`，这个公式是对的（除以 k 得到的是 Precision@k）。
但 gold set 是**人工标注的、仅针对当前问题的最相关那一小撮文档**，不是"库里所有沾边的内容"。
权威数据集（MS MARCO、KILT）的标准相关集通常只有 1~5 篇，极少超过 10。

之前用"同一文件的全部 chunk"当 gold set，于是 `big-integer/README.md` 的 58 个 chunk 全被算成与
"how do I use big integer" 相关，包括：

```
#### shiftLeft(n)     Shifts the number left by n places...
#### square()         Squares the number - bigInt(3).square() => 9
#### subtract(number) Performs subtraction...
```

`shiftLeft` 与该查询没有任何词汇或语义重叠，**任何检索器都不该把它排进前 10——排进去反而是错的**。
分母里塞满了文本上无法被这条查询检索到的内容。

### 22.2 改法与效果

按 h1~h4 **小节**划分 gold set。实测本语料 4058 个小节的 chunk 数分布：

| gold set 大小 | 小节数 |
|---|---|
| 1 | 3327 |
| 2 | 447 |
| 3 | 171 |
| 4 | 68 |
| 5 | 17 |
| 6+ | 28 |

**99% 落在 1~5 个 chunk**，正好是权威数据集的量级。上限取 8 以保留少量偏长小节。

查询改用小节标题——它是文档作者写的"这一节讲什么"，是不看正文就能得到的最贴近查询意图的文本。
前面拼包名/文件名消歧，因为 `## Installation`、`## License` 这类标题在 node_modules 里大量重复，
不消歧会让同一句查询对应多个 gold set。

同一套检索器、同一份语料、同一个公式，只换 gold set 定义：

| gold set 定义 | 规模 | R@10 | 上限 | 达上限 |
|---|---|---|---|---|
| 文件级（错） | 8~58 | 0.274 | 0.6505 | 43% |
| **小节级（对）** | **1~8（均值 1.34）** | **0.701** | **1.000** | **70%** |

R@10 涨 2.6 倍，理论上限从 0.6505 变成 1.000（gold set 都 ≤10，取 10 条足以全覆盖）。
**"检索能力只有四成"这个读法是分母错误的产物。**

### 22.3 修正后的完整结果

5460 chunk，3995 个可查询小节，等距抽样 300 条查询：

| 场景 | R@1 | R@5 | R@10 | MRR | nDCG@10 | 零结果 | p50 |
|---|---|---|---|---|---|---|---|
| hybrid-natural-rerank | 0.418 | 0.643 | **0.706** | 0.572 | 0.579 | 0 | 372ms |
| vector-only-natural | 0.420 | 0.637 | 0.701 | 0.569 | 0.578 | 0 | 248ms |
| hybrid-natural | 0.403 | 0.630 | 0.687 | 0.561 | 0.566 | 0 | 251ms |
| lexical-only-natural | 0.159 | 0.347 | 0.474 | 0.297 | 0.316 | 57 | 9ms |

重排 +0.005 R@10 换 +124ms（+50%），这套语料上不值得默认开启。

### 22.4 剩下 30% 未命中的成因

不是检索缺陷，是**查询信息量**：

| 标题去掉编号后长度 | 查询数 | R@10 |
|---|---|---|
| ≤6 字符（"职责"、"产品定位"、"平台架构"） | 58 | **0.384** |
| >6 字符 | 242 | **0.777** |

"D.1 职责"这种标题本身就不足以定位到唯一小节——换成人也做不到。这是评测语料的性质，不是缺陷。

### 22.5 lexical 的 57 条零结果：不改门槛

零结果全部是版本号标题（`in async, v2.6.0` 这类 CHANGELOG 小节），**与中文分词无关**。成因是查询
构造与门槛的交互：包名来自路径、正文里不出现，正确 chunk 含 `v2.6.0` 而不含 `async`，全库同时含
两词的 chunk 为 0，2 实词门槛必然排除它。

放宽门槛已实测，是净损失：

| 最少实词命中 | R@1 | 命中率@10 | 零结果 | P@10 |
|---|---|---|---|---|
| 1 | 0.103 | 0.387 | 0 | 0.044 |
| **2（保持）** | **0.133** | **0.467** | 72 | **0.078** |

三项全跌、P@10 几乎腰斩，因为单个实词命中会把大量无关 chunk 灌进列表。且 hybrid 场景零结果本来
就是 0（向量腿覆盖），产品侧无需改动。

## 23. 把 R@10 从 0.706 提到 0.912

目标是 R@10 > 0.85。过程里排除了 6 条无效杠杆，最终靠 3 处修复达标——都是产品缺陷，不是调参。

### 23.1 先定位瓶颈，不盲目调参

把正确答案在向量检索结果里的排名统计出来（深度 200）：

| 排名 | 占比 |
|---|---|
| 第 1 位 | 44.0% |
| 2~10 位 | 36.7% |
| 11~50 位 | 10.3% |
| 51~200 位 | 3.3% |
| 未进前 200 | 5.7% |

前 10 合计 80.7%，理论可达 94.3%。说明大部分正确答案检索得到，问题在排序与管线损耗。

### 23.2 被实测排除的 6 条杠杆

| 杠杆 | 结果 |
|---|---|
| `candidate_k` 24 → 50 → 100 → 200 | +1.3% 后饱和 |
| 重排 24/50/100/200 深度 | **-1.6% ~ -0.3%（有害）** |
| 同小节兄弟 chunk 扩展（每条都扩） | **-2.7%** |
| 同小节兄弟扩展（仅第 1 名） | +0.5% |
| RRF k 值 10/20/40/60 | 0.764~0.776，无显著差异 |
| 向量:词法权重 1:1 ~ 5:1、双查询融合 | 0.718~0.776 |

全部落在 0.75~0.78。融合与选择层已经调不动了，瓶颈在别处。

### 23.3 缺陷一：评测产物污染语料

`docs/evaluation-report.md` 本身进了语料，而它逐字包含查询文本——报告里写着
`≤6 字符（如"职责"、"产品定位"）`，查询就是 `in ..., 1. 产品定位`。48 个 chunk 含 "R@10"。

双向都错：报告的 chunk 作为竞争者挤掉真正的小节，而报告自己的小节也进了 gold set，检索到它算
"命中"。已把评测产物从语料排除。这是实验设计修正，不是调参。

### 23.4 缺陷二：chunk 丢失标题上下文

一个小节被切成多个 chunk 时，**只有第 1 个带标题行**，其余是纯正文。前 800 个 chunk 里只有 77%
以标题开头。

产品侧后果比跑分更重要：Agent 拿到一个中段 chunk 时不知道它属于哪一节，引用和上下文都缺失。

修复是把标题路径（含父级，`# pi-ai > ## Overview`）前置到每个 chunk。效果精确命中诊断：

| 分组 | 修复前 | 修复后 |
|---|---|---|
| gold set = 1 | 0.759 | 0.788 |
| **gold set > 1** | **0.502** | **0.692** |

多 chunk 小节涨 38%，正是缺少标题上下文的那一组。整体 0.706 → 0.769。

### 23.5 缺陷三：文档标识不可检索

文档自身的标识（包名/文件名）只存在 `entity_keys` 里，**不在可检索文本里**。查询提到 `exceljs`
时，`exceljs/README.md` 的正文可能根本不含这个词，词法腿匹配不上，向量腿也拿不到信号。

修复是把文档标识也放进上下文前缀。整体 0.769 → **0.912**，词法腿 0.543 → 0.868。

我先试过另一种做法：从查询解析来源、把同源 chunk 加权提前，达到 0.863。放弃了，因为那是给 RRF
外挂特判、且依赖我构造的查询格式。改成把标识写进可检索文本后，普通检索自然用得上，不需要任何
特殊加权。

**适用条件**：收益依赖查询提供来源。查询去掉来源后收益消失（0.783 vs 无标识的 0.799）。

不是标签泄漏，三条理由：标识只到*文件*层而 gold set 是 (文件, 小节)，exceljs 的 100+ 小节共享同一
标识，无法指明哪一节；标题唯一组 0.914 与标题重复组 0.905 几乎相同，若收益只来自消歧则重复组才该
独涨；R@1 仍只有 0.565，说明仍需在同文件上百个小节中排序。

### 23.6 修复四：查询侧 instruct 前缀

Qwen3 embedding 训练时查询用 `Instruct: <任务>
Query: <查询>` 格式，文档侧不加。两侧都不加会丢
掉这部分训练信号。

| 查询格式 | R@10 | R@1 |
|---|---|---|
| 原样 | 0.720 | 0.410 |
| **`Instruct: ...` 前缀** | **0.754** | **0.425** |
| 对照：`query: ` 前缀 | 0.737 | 0.410 |

对照组只到 0.737，说明收益来自模型认识这个具体格式，不是"加了点前缀"。已实现在
`PostgresVectorRetriever`，只作用于查询侧（文档向量不带前缀，与训练时的非对称用法一致，所以不需要
重建索引），并留了 `query_instruction: false` 开关——前缀与模型绑定，换 embedding 模型时必须重测。

### 23.7 顺带修复：重排 provider 兼容性

跑重排实验时整条链路报 `PROVIDER_ERROR`。本地部署的 Qwen3-VL-Embedding-2B 的 `/v1/rerank`
**忽略请求里的 `top_k`**，总是返回全部文档的打分（请求 top_k=3、5 篇文档，返回 5 条），而客户端
断言"恰好 top_k 条"。

服务端截断是可选优化不是协议保证（Cohere、Jina 会截，vLLM 一类打分端点通常不截）。已改成"至少
top_k 条"并由客户端按分数降序自己截断；少于 top_k 仍是错误，那说明 provider 没给够结果。

这个缺陷让整个重排能力对这类 provider 完全不可用，尽管它的打分本身是正确的。
